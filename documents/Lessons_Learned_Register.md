# สมุดบันทึกการถอดบทเรียน (Lessons Learned Register)
**มาตรฐานอ้างอิง:** ISO/IEC 12207 (กระบวนการประเมินและควบคุมโครงการ และการจัดการความรู้ขององค์กร), ISO/IEC 14764:2006 (กระบวนการบำรุงรักษาซอฟต์แวร์)
**รายวิชา:** ENGSE225 Software Evolution & Maintenance

## วัตถุประสงค์ของเอกสาร

เอกสารฉบับนี้รวบรวมบทเรียนที่ได้รับตลอดโครงการ Inventory Management System ระหว่างวันที่ 12 กรกฎาคม 2026 ถึง 5 ตุลาคม 2026 ทั้งปัญหาที่พบและแนวปฏิบัติที่ได้ผลดี เพื่อนำไปจัดเก็บเป็นสินทรัพย์กระบวนการขององค์กร (Organizational Process Assets: OPAs) สำหรับใช้ในโครงการถัดไป

**วิธีอ่านเอกสาร**
- ส่วนที่ 1 สรุปบทเรียนทั้งหมดในตารางเดียว เหมาะสำหรับผู้บริหารที่ต้องการภาพรวม
- ส่วนที่ 2 อธิบายบทเรียนแต่ละข้อในรูปแบบเดียวกัน ได้แก่ เหตุการณ์ สาเหตุ การแก้ไขที่ดำเนินการแล้ว ข้อเสนอแนะ และสินทรัพย์ที่ต้องปรับปรุง
- ส่วนที่ 3 ระบุงานปรับปรุงสินทรัพย์กระบวนการพร้อมผู้รับผิดชอบ

## ส่วนที่ 2: รายละเอียดบทเรียน

### LL-01 ไฟล์ที่ระบบสร้างขึ้นเองถูกบันทึกเข้าคลังโค้ดซ้ำ
- **เหตุการณ์:** commit `fe64f8c` บันทึกไฟล์ `__pycache__`, `inventory.db` และ `inventory.log` เข้าคลังโค้ด ทีมได้ลบออกใน commit `36214fc` แต่ต่อมา commit `85d5b44` นำไฟล์ประเภทเดียวกันกลับเข้ามาอีก จึงต้องลบซ้ำใน commit `39475bf` และ `6a57284`
- **สาเหตุ:** ไฟล์ `.gitignore` ถูกลบไปพร้อมไฟล์ต้นแบบเดิม (commit `32f55b0`) และสร้างขึ้นใหม่หลังจากเริ่มเขียนโค้ดไปแล้ว
- **การแก้ไขที่ดำเนินการแล้ว:** ไฟล์ `.gitignore` ปัจจุบันครอบคลุม `*.db`, `__pycache__/` และ `.venv/`
- **ข้อเสนอแนะ:** เริ่มคลังโค้ดจากแม่แบบที่มี `.gitignore` และ `.gitattributes` ตั้งแต่ commit แรก และตรวจสอบรายการไฟล์ด้วยคำสั่ง `git status` ก่อนบันทึกทุกครั้ง
- **สินทรัพย์ที่ต้องปรับปรุง:** แม่แบบคลังโค้ด (Repository Template), รายการตรวจสอบก่อนบันทึกโค้ด (Commit Checklist)

### LL-02 การรวมโค้ด CR-01 ครั้งแรกไม่สมบูรณ์
- **เหตุการณ์:** หลังรวมโค้ดผ่าน PR #20 ทีมต้องยกเลิกการรวมผ่าน PR #21 และ #22 (commit `c8fc769`) แล้วดำเนินการใหม่ใน commit `75af8d2` ผ่าน PR #23
- **สาเหตุ:** รวมโค้ดก่อนปรับ branch ให้ตรงกับ `develop` และในขณะนั้นยังไม่มีระบบทดสอบอัตโนมัติที่บังคับให้ผ่านก่อนรวมโค้ด
- **การแก้ไขที่ดำเนินการแล้ว:** ระบบ CI ทดสอบโค้ดทุกคำขอรวมโค้ด และเกณฑ์ความสำเร็จของงาน (Definition of Done: DoD) ข้อ 3 กำหนดให้ผ่าน CI และได้รับอนุมัติจากผู้ทดสอบก่อนรวมโค้ด
- **ข้อเสนอแนะ:** ตั้งค่าการป้องกัน branch (Branch Protection) บน GitHub ให้บังคับเงื่อนไขดังกล่าวในระบบ และปรับ branch ให้ตรงกับ `develop` ก่อนส่งคำขอรวมโค้ดทุกครั้ง
- **สินทรัพย์ที่ต้องปรับปรุง:** แนวปฏิบัติการจัดการ branch และการรวมโค้ด, รายการตรวจสอบคำขอรวมโค้ด

### LL-03 การย้อนกลับทั้ง branch ทำให้ติดตามประวัติได้ยาก
- **เหตุการณ์:** PR #18 (`rollback-to-0c95308`) และ commit `a94fda0` ลบและนำไฟล์จำนวนมากกลับมา ตามด้วยการแก้ไขความขัดแย้งของโค้ดใน commit `5084235` ส่งผลให้ไม่สามารถสรุปการเปลี่ยนแปลงช่วงนี้ลงในบันทึกประวัติการเปลี่ยนแปลง (CHANGELOG) ได้อย่างแม่นยำ
- **สาเหตุ:** ใช้วิธีย้อนกลับทั้ง branch แทนการยกเลิกเฉพาะ commit ที่มีปัญหา
- **ข้อเสนอแนะ:** ใช้คำสั่ง `git revert` กับ commit ที่มีปัญหาเท่านั้น และส่งผ่านคำขอรวมโค้ดพร้อมระบุเหตุผล การย้อนกลับทั้ง branch ต้องได้รับอนุมัติจากหัวหน้าฝ่ายเทคนิค
- **สินทรัพย์ที่ต้องปรับปรุง:** แนวปฏิบัติการจัดการ branch และการรวมโค้ด

### LL-04 ไฟล์กำหนดการทำงานของ CI อยู่ผิดตำแหน่ง
- **เหตุการณ์:** ไฟล์ `tests.yml` ถูกเพิ่มไว้ที่โฟลเดอร์หลักของโครงการ (commit `2c8710d`) ระบบ CI จึงไม่ทำงาน จนกระทั่งย้ายไปไว้ที่ `.github/workflows/` ใน commit `8d14fee`
- **ข้อเสนอแนะ:** ยืนยันว่าระบบ CI ทำงานจริงด้วยการส่งคำขอรวมโค้ดทดลอง ไม่ควรตรวจเพียงว่ามีไฟล์อยู่ในคลังโค้ด
- **สินทรัพย์ที่ต้องปรับปรุง:** แม่แบบคลังโค้ดที่มีโฟลเดอร์ `.github/workflows/` พร้อมใช้งาน

### LL-05 ข้อบกพร่องด้านรูปแบบโค้ดและความปลอดภัยสะสม
- **เหตุการณ์:** การตรวจสอบครั้งแรกพบข้อบกพร่องจาก Flake8 (เครื่องมือตรวจรูปแบบโค้ด) 410 รายการ และจาก Bandit (เครื่องมือตรวจความปลอดภัย) 196 รายการ ทีมต้องแก้ไขทั้งหมดในครั้งเดียวใน commit `6358919`
- **สาเหตุ:** เพิ่มเครื่องมือทั้งสองเข้าสู่ระบบ CI ในสัปดาห์ท้ายของโครงการ
- **การแก้ไขที่ดำเนินการแล้ว:** ระบบ CI บังคับให้ผลตรวจของ Flake8 และ Bandit เป็นศูนย์ และระบุเวอร์ชันของเครื่องมือไว้ใน `requirements-dev.txt`
- **ข้อเสนอแนะ:** เปิดใช้การตรวจทั้งสองประเภทตั้งแต่รอบการพัฒนา (Sprint) แรก และระบุเวอร์ชันของไลบรารีที่เครื่องมือเรียกใช้ด้วย เนื่องจากพบว่า pyflakes เปลี่ยนจากเวอร์ชัน 4.0.1 เป็น 4.0.2 เองโดยไม่มีการแก้ไขโค้ด
- **สินทรัพย์ที่ต้องปรับปรุง:** แม่แบบระบบ CI, มาตรฐานการเขียนโค้ด

### LL-06 เอกสารไม่สอดคล้องกับโค้ด
- **เหตุการณ์:** พบความไม่สอดคล้องหลายจุด ได้แก่
  - README ระบุจำนวนชุดทดสอบ 119 รายการ ขณะที่มีอยู่จริง 138 รายการ
  - ทะเบียนคำขอเปลี่ยนแปลงยังระบุว่า CR-02 "รอรวมโค้ด"
  - รายงาน CR-02 ยังอธิบายวิธีเขียนไฟล์แบบเดิม
  - รายงาน CR-01 มีเครื่องหมาย `[cite: …]` หลงเหลือ 51 จุด
  - CHANGELOG ฉบับแรกระบุว่าคลังโค้ดยังไม่มีป้ายกำกับเวอร์ชัน (tag) ทั้งที่มี `v1.0.0` อยู่แล้ว ซึ่งได้แก้ไขพร้อมการจัดทำเอกสารฉบับนี้
- **สาเหตุ:** เกณฑ์ความสำเร็จของงานไม่ได้กำหนดให้ปรับปรุงเอกสารในคำขอรวมโค้ดเดียวกับการแก้โค้ด และผู้จัดทำเอกสารไม่ได้ตรวจสอบข้อมูลจากคลังโค้ดบนเซิร์ฟเวอร์ก่อนเขียน
- **การแก้ไขที่ดำเนินการแล้ว:** ปรับปรุงเอกสารทั้งหมดใน commit `31471c5` และปรับชื่อเวอร์ชันใน CHANGELOG ให้ตรงกับ tag ที่มีอยู่จริง
- **ข้อเสนอแนะ:** เพิ่มข้อกำหนดในแม่แบบคำขอรวมโค้ดให้ปรับปรุง README, CHANGELOG และทะเบียนคำขอเปลี่ยนแปลงไปพร้อมกับโค้ด และให้ผู้ทดสอบตรวจตัวเลขในเอกสารเทียบกับผลการทดสอบจริง
- **สินทรัพย์ที่ต้องปรับปรุง:** เกณฑ์ความสำเร็จของงาน (DoD), แม่แบบคำขอรวมโค้ด

### LL-07 ชุดทดสอบไม่ครอบคลุมค่าขอบเขตของข้อมูลนำเข้า
- **เหตุการณ์:** ข้อบกพร่อง 3 รายการไม่ถูกตรวจพบโดยชุดทดสอบ 138 รายการที่มีอยู่ ได้แก่
  - BUG-103 ค่า `nan` และ `inf` ผ่านการตรวจสอบราคา เพราะการเปรียบเทียบ `nan < 0` ให้ผลเป็นเท็จ
  - BUG-105 ตัวเลขที่เกิน 2⁶³−1 ทำให้โปรแกรมหยุดทำงาน
  - BUG-108 ระบบยอมรับการตัดสต็อกจำนวน 0 ชิ้น
- **สาเหตุ:** ชุดทดสอบออกแบบจากกรณีการใช้งานปกติและค่าติดลบ โดยไม่มีรายการตรวจสอบค่าขอบเขตของชนิดข้อมูล
- **การแก้ไขที่ดำเนินการแล้ว:** เพิ่มชุดทดสอบ 18 รายการสำหรับ BUG-103 ถึง BUG-108 (BUG-103 จำนวน 5 รายการ และ BUG-104 ถึง BUG-108 จำนวน 13 รายการ) และกำหนดค่าคงที่ `SQLITE_MAX_INTEGER`
- **ข้อเสนอแนะ:** ใช้รายการตรวจสอบค่าขอบเขตกับข้อมูลนำเข้าที่เป็นตัวเลขทุกจุด ได้แก่ ศูนย์ ค่าติดลบ ค่าสูงสุดของชนิดข้อมูลปลายทาง `nan` `inf` ค่าว่าง และตัวอักษร
- **สินทรัพย์ที่ต้องปรับปรุง:** รายการตรวจสอบการออกแบบกรณีทดสอบ

### LL-08 ไม่ได้ทดสอบไฟล์ด้วยโปรแกรมที่ผู้ใช้ใช้งานจริง
- **เหตุการณ์:** BUG-106 ไฟล์ CSV ผ่านชุดทดสอบทุกรายการ เพราะชุดทดสอบอ่านไฟล์ด้วย Python ในรูปแบบ UTF-8 แต่เมื่อฝ่ายจัดซื้อเปิดไฟล์ด้วย Excel ซึ่งใช้รหัสอักขระของเครื่อง (code page 874) ชื่อสินค้าภาษาไทยไม่สามารถอ่านได้ ขัดกับวัตถุประสงค์ของ CR-02 ที่กำหนดให้ "เปิดใน Excel ได้ทันที"
- **สาเหตุ:** เกณฑ์การยอมรับของ CR-02 ไม่ได้ระบุให้ทดสอบด้วยโปรแกรมที่ผู้ใช้ใช้งานจริง
- **การแก้ไขที่ดำเนินการแล้ว:** เปลี่ยนการเขียนไฟล์ CSV เป็น `utf-8-sig` และยืนยันผลด้วยการเปิดใน Excel ระหว่างการทดสอบการยอมรับรอบที่ 2
- **ข้อเสนอแนะ:** คำขอเปลี่ยนแปลงที่มีการส่งออกไฟล์ต้องมีกรณีทดสอบที่เปิดไฟล์ด้วยโปรแกรมปลายทางจริงบนเครื่องที่ตั้งค่าภาษาเดียวกับผู้ใช้
- **สินทรัพย์ที่ต้องปรับปรุง:** แม่แบบรายงานคำขอเปลี่ยนแปลง (ส่วนเกณฑ์การยอมรับ), รายการตรวจสอบการทดสอบการยอมรับ

### LL-09 คำว่า "สินค้าใกล้หมด" มีสองความหมาย

### LL-10 ปัญหาเฉพาะของ Windows ที่ตั้งค่าภาษาไทย
- **เหตุการณ์:** พบปัญหา 5 ลักษณะ ได้แก่
  - การเปิดไฟล์ `schema.sql` โดยไม่ระบุรหัสอักขระทำให้เกิด `UnicodeDecodeError`
  - PowerShell ไม่รองรับคำสั่ง `sqlite3 inventory.db < seed_data.sql`
  - Windows PowerShell 5.1 แปลงข้อความที่ส่งต่อ (pipe) ให้ Python เป็นรหัส ASCII ทำให้ภาษาไทยกลายเป็น `?` และการทดสอบเบื้องต้นเกิด `EOFError`
  - การตั้งค่า `core.autocrlf=true` อาจเปลี่ยนรูปแบบการขึ้นบรรทัดใหม่ของไฟล์ `.sh` จน bash ไม่สามารถทำงานได้
  - เครื่องมือแก้ไขไฟล์บางตัว เช่น `sed -i` ใน Git Bash เปลี่ยนรูปแบบการขึ้นบรรทัดใหม่โดยไม่แจ้งเตือน
- **การแก้ไขที่ดำเนินการแล้ว:** ระบุ `encoding='utf-8'` ทุกจุด เพิ่มไฟล์ `.gitattributes` ให้สคริปต์ติดตั้งเรียกโค้ด Python ผ่านไฟล์ชั่วคราว บันทึก `setup.ps1` เป็น UTF-8 แบบมี BOM และเขียน `setup.cmd` ด้วยอักขระ ASCII เท่านั้น
- **ข้อเสนอแนะ:** จัดทำรายการตรวจสอบความเข้ากันได้ข้ามระบบปฏิบัติการ ครอบคลุมรหัสอักขระ รูปแบบการขึ้นบรรทัดใหม่ และการส่งต่อข้อมูลระหว่างคำสั่ง และทดสอบทั้งบน PowerShell และ bash ก่อนส่งมอบ
- **สินทรัพย์ที่ต้องปรับปรุง:** มาตรฐานการเขียนโค้ด, คู่มือการเตรียมสภาพแวดล้อม

### LL-11 ชุดทดสอบให้ผลต่างกันตามระบบปฏิบัติการ
- **เหตุการณ์:** ระหว่างเขียนชุดทดสอบของ BUG-104 พบว่าชื่อไฟล์ `report?.csv` ทำให้เกิดข้อผิดพลาดบน Windows แต่สามารถสร้างไฟล์ได้บน Linux ซึ่งเป็นระบบที่ CI ใช้ จึงเปลี่ยนไปใช้กรณีที่เกิดข้อผิดพลาดได้ทุกระบบปฏิบัติการก่อนบันทึกโค้ด
- **ข้อเสนอแนะ:** ชุดทดสอบที่อาศัยพฤติกรรมของระบบไฟล์ต้องพิจารณาทุกระบบปฏิบัติการที่ CI ใช้ทดสอบ
- **สินทรัพย์ที่ต้องปรับปรุง:** รายการตรวจสอบการออกแบบกรณีทดสอบ

### LL-12 ส่งการแก้ไขเข้าสู่ branch หลักโดยไม่ผ่านการตรวจทาน
- **เหตุการณ์:** หลัง PR #33 มีการส่ง commit จำนวน 15 รายการ (ตั้งแต่ `d347d8e` ถึง `441b2ea`) เข้าสู่ branch `main` โดยตรง ซึ่งรวมถึงการแก้ไขโค้ดของ BUG-103 ถึง BUG-108 ส่งผลให้ branch `develop` ไม่เป็นปัจจุบัน และขัดกับเกณฑ์ความสำเร็จของงานข้อ 3
- **สาเหตุ:** ความเร่งรีบในช่วงปิดโครงการ และยังไม่ได้ตั้งค่าการป้องกัน branch ในระบบ
- **การแก้ไขที่ดำเนินการแล้ว:** ทุก commit ผ่านการทดสอบถดถอย (Regression Test) บนเครื่องก่อนส่ง และได้บันทึกการปฏิบัติที่ไม่เป็นไปตามกระบวนการไว้ในรายงานการทดสอบการยอมรับและตารางประเมินผลโครงการ
- **ข้อเสนอแนะ:** เปิดใช้การป้องกัน branch `main` และ `develop` ตลอดโครงการ แม้ในช่วงเร่งด่วน และใช้ช่องทางแก้ไขเร่งด่วน (branch `bugfix/*` ผ่านคำขอรวมโค้ด) แทนการส่งโค้ดโดยตรง
- **สินทรัพย์ที่ต้องปรับปรุง:** แนวปฏิบัติการจัดการ branch และการรวมโค้ด, รายการตรวจสอบการปล่อยระบบ

### LL-13 แก้ไขข้อบกพร่องระดับเล็กน้อยระหว่างช่วงล็อกขอบเขต
- **เหตุการณ์:** BUG-107 และ BUG-108 ซึ่งเป็นข้อบกพร่องระดับเล็กน้อย (Minor) ได้รับการแก้ไขในสัปดาห์ที่ 12 ทั้งที่ข้อ 5.2 ของสัญญาล็อกขอบเขต (SFA-01) อนุญาตเฉพาะข้อบกพร่องระดับวิกฤต (Critical) หรือระดับที่ขัดขวางการใช้งาน (Blocker) จากนั้นจึงขอให้ผู้สนับสนุนโครงการ (Sponsor) รับทราบในการลงนาม
- **ข้อเสนอแนะ:** แม่แบบสัญญาล็อกขอบเขตควรมีช่องทางสำหรับการแก้ไขระดับเล็กน้อยที่มีความเสี่ยงต่ำ โดยต้องได้รับอนุมัติล่วงหน้า แทนการขอรับทราบภายหลัง
- **สินทรัพย์ที่ต้องปรับปรุง:** แม่แบบสัญญาล็อกขอบเขต

### LL-14 ไม่มีข้อมูลกำหนดการและต้นทุนจริง
- **เหตุการณ์:** รายงานคำขอเปลี่ยนแปลงมีเพียงชั่วโมงทำงานที่ประมาณการไว้ (CR-01 จำนวน 8 ชั่วโมง และ CR-02 จำนวน 4.5 ชั่วโมง) โดยไม่มีชั่วโมงทำงานจริงและวันที่ตามแผน ตารางประเมินผลโครงการจึงไม่สามารถประเมินด้านกำหนดเวลาและต้นทุนได้
- **ข้อเสนอแนะ:** บันทึกชั่วโมงทำงาน (Work Log) ใน Jira ทุกรายการงาน และกำหนดวันที่ตามแผนของแต่ละหมุดหมาย (Milestone) ตั้งแต่เริ่มโครงการ เพื่อให้สามารถคำนวณดัชนีวัดผลงานด้านเวลา (SPI) ดัชนีวัดผลงานด้านต้นทุน (CPI) และส่วนต่างต้นทุน ($CV = EV - AC$) ได้
- **สินทรัพย์ที่ต้องปรับปรุง:** แม่แบบแผนโครงการ, ขั้นตอนการทำงานบน Jira

### LL-15 ไม่ได้แนบผลการทดสอบอัตโนมัติไว้ในเอกสารปิดโครงการ
- **เหตุการณ์:** หนังสือรับรองการปิดเฟส รายงานตัวชี้วัดทางเทคนิค และตารางประเมินผลโครงการ ต้องระบุสถานะ "รอหลักฐาน" ในเกณฑ์ด้าน CI เนื่องจากยังไม่ได้แนบผลจาก GitHub Actions ของ build ที่ส่งมอบ
- **ข้อเสนอแนะ:** รายการตรวจสอบการปล่อยระบบต้องมีขั้นตอน "แนบลิงก์ผล CI ของ commit ที่สร้าง tag" ก่อนออกเอกสารปิดโครงการ
- **สินทรัพย์ที่ต้องปรับปรุง:** รายการตรวจสอบการปล่อยระบบ

### LL-16 ✅ การทดสอบการยอมรับตามสถานการณ์ธุรกิจจริง
- **เหตุการณ์:** การทดสอบการยอมรับโดยผู้ใช้ (UAT) จำนวน 17 สถานการณ์ จำลองการทำงานของพนักงานคลังสินค้า ฝ่ายจัดซื้อ และผู้จัดการร้านกับโปรแกรมจริง พบข้อบกพร่อง 5 รายการ และความต้องการใหม่ 5 รายการ ทั้งที่ชุดทดสอบหน่วย (Unit Test) และชุดทดสอบการทำงานร่วมกัน (Integration Test) ผ่านครบ 145 รายการ

- **สินทรัพย์ที่ต้องปรับปรุง:** แม่แบบรายงานการทดสอบการยอมรับ, แนวทางการจำแนกข้อบกพร่องและความต้องการใหม่

### LL-17 ✅ เขียนชุดทดสอบให้ล้มเหลวก่อนแก้ไขข้อบกพร่อง
- **เหตุการณ์:** การแก้ไข BUG-103 ถึง BUG-108 ทุกรายการเริ่มจากการเขียนชุดทดสอบที่ล้มเหลว (ขั้น Red) แล้วจึงแก้ไขโค้ดจนชุดทดสอบผ่าน (ขั้น Green) และยังนำชุดทดสอบเดียวกันไปรันกับโค้ดก่อนแก้ไข เพื่อยืนยันว่าชุดทดสอบตรวจพบข้อบกพร่องได้จริง

- **สินทรัพย์ที่ต้องปรับปรุง:** แนวปฏิบัติกระบวนการบำรุงรักษาตาม ISO/IEC 14764

### LL-18 ✅ การใช้รายการงานสำหรับเวอร์ชันถัดไปร่วมกับการล็อกขอบเขต

### LL-20 ✅ การทดสอบติดตั้งบนเครื่องที่ไม่เคยติดตั้งระบบมาก่อน
- **เหตุการณ์:** การรันสคริปต์ติดตั้งบนสำเนาคลังโค้ดที่ดาวน์โหลดใหม่ (clone) ครั้งแรก พบปัญหาของ PowerShell 5.1 ตาม LL-10 ซึ่งไม่เกิดขึ้นบนเครื่องของนักพัฒนาที่ติดตั้งสภาพแวดล้อมไว้แล้ว
- **แนวปฏิบัติที่ควรใช้ต่อ:** ทดสอบการติดตั้งบนสภาพแวดล้อมใหม่ (Clean Environment Installation Test) ทุกครั้งก่อนส่งมอบ และเพิ่มขั้นตอนนี้เข้าสู่ระบบ CI
- **สินทรัพย์ที่ต้องปรับปรุง:** รายการตรวจสอบการปล่อยระบบ, แม่แบบระบบ CI
